## How each check works

- **Hard constraints** are re-derived from `ACTIVITIES` by a separate oracle in run.ts (time slot, stairs vs walker/wheelchair, a mode the person has whose minutes are within their limit, cost). Every planned item, plus the plan's total cost, is checked against it. Walking only counts for full/cane mobility (the product's rule). The oracle never calls engine code.
- **Soft barriers** on every planned item must equal the oracle's set exactly (cane + stairs, family-only or paratransit ride, noisy room without a hearing loop for a hearing-impaired person, large group for someone who prefers small groups), each with a mitigation. A dropped or mislabeled hearing/social barrier fails.
- **Score + route + ranking**: each item's score and route must equal the recomputed ones, and the plan must equal the oracle's greedy plan (best score first, ties by id A→Z, one per day, ≤3, cumulative budget).
- **Blocked**: every blocked activity has ≥1 hard barrier, every hard barrier is true per the oracle, no true reason is missing, and the blocked set equals the oracle's infeasible set.
- **Maximal**: with fewer than 3 items, no feasible activity on a free day that fits the remaining budget was left out.
- **Determinism / order / name**: same input twice, reversed arrays, and name→"Zed" all give the same plan.
- **Sensitivity** flips one field (mobility ×3, add drive, remove family, times, budget ×2, travel ×2, hearing, small groups) and re-runs every check above, plus forced-change rules: budget→$0 must leave no paid item; travel→5 min must give an EMPTY plan (asserted, because the closest venue in the catalog is 6 min).
- **Exit code** is 0 only if every check ran and passed: an unreachable API, a skipped case, a schema-invalid person, bad input not rejected with 400, a contract break, or a missed negative control all exit 1.

## Observations (product behavior, not bugs)

- Walker and wheelchair users never get a "walk" route, so a walker user whose only mode is walk (Clara) gets nothing. That's the intended rule, but the profile form still lets them pick walk only.
- The plan allows one activity per day, so two feasible activities on the same day can't both be planned even at different times (e.g. Lakeside Morning Walkers, Mon morning, and Ukulele & Singing, Mon afternoon).
- Scoring is 10 × matching interests − 2 × soft barriers − travel/10, so people with many interests converge on the two-tag, close-by venues (Library Cards + Tech Hour); see "Distinct plans" for who shares what.
- Equal scores are broken by activity id alphabetically. That is deterministic but arbitrary; the "Tie decides?" column and the TIE notes show where it picks the plan.
- When family and another mode both fit, the engine prefers the independent mode even if family is faster (by design: "prefer an independent route").
