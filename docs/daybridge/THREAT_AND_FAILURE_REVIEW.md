## Trust boundaries and proposed controls

1. **User input / model output -> confirmed facts:** Validate schemas, preserve unknowns, bind confirmation to displayed values and profile version. Intake defaults for budget/travel in the lead handoff are proposals, not user-confirmed limits. Never infer a diagnosis or protected trait; explicit sensitive preferences require review.
2. **UI command -> API actor authority:** A body `actor: user`, `approved: true` or guessed plan id is not authorization. For an isolated single-user fixture demo, explicitly define that limited trust model and keep adapters mock-only. For shared/multi-user use, lead must supply real ownership enforcement; do not add an auth stack implicitly.
3. **Approval -> dispatch:** Bind actor, plan/version, action, recipient/target, exact disclosure, time window and cost ceiling to server-controlled records. Reject changed recipient, price, payload or plan scope. Revocation blocks unsent work. Cancellation of already-sent work may itself require a provider operation and must retain its true outcome; do not erase history.
4. **Provider callback -> dependency evidence:** Authenticate live callbacks if introduced; demo events are explicitly simulated. Correlate provider/request/dependency identity, event id and applicable revision. Handle retries idempotently; deduplicate logical actions across fresh event ids. Persist dispatch state sufficiently to survive uncertain delivery. Do not blindly retry a send after timeout.
5. **Event -> READY/COMPLETED:** READY is computed from current valid dependencies and approvals, never client-submitted state. Unknown/pending/declined required dependencies block it. Cancellation is durable; late confirms for superseded requests cannot overwrite it. Optional invitee decline need not block readiness. RSVP/event time passing is not verified attendance.
6. **Profile/plan -> AI/store/share:** Minimize payloads and logs; separate private constraints from peer-visible details. Model endpoint is operator-configured, not user-controlled today; arbitrary URL SSRF is not established by this code. Allowing users to set URLs later would require a separate endpoint policy. Shared links need revocation and a restricted read path; a UUID and hidden name do not by themselves protect profile JSON.

## Baseline observations to preserve as regression cases

- Family-only profile can produce a nonempty plan plus transport `verified: true`, while each item still says to ask family. This must stay a conditional recommendation until an actual dependency confirms.
- Model explanation content is free text, separate from deterministic output. A false “ride booked” response must not be trusted just because `dataSource` becomes `live`.
- `Profile` has no contact/day fields; unsupported additions can be stripped by object parsing. Callers must not assume those constraints were enforced merely because validation succeeded.
- Existing tests depend on named Margaret/choir catalog fixtures (`src/domain/engine.test.ts:6–18`). B replacing data can break safety tests or weaken their meaning; isolate synthetic invariants in GLM's assigned paths.
