## Architecture assessment

| Area | Finding | Consequence / recommendation |
|---|---|---|
| Deterministic/AI separation | Domain code has no AI calls; route computes output before explanation. Good baseline boundary. | Retain it. LLM text must never grant approval, mutate constraints, create provider evidence or set READY. |
| Explanation trust | [`src/lib/ai/adapter.ts:21–56`](https://github.com/dude297/c0mpiled-hackathon/blob/26b976233f53d3dede16a92416258e8a3c464cdb/src/lib/ai/adapter.ts#L21-L56) relies on a prompt and accepts any nonempty coerced model content. | Fabricated confirmation language can be displayed despite unchanged domain output. Lead should validate response shape and constrain/verify consequential claims or use deterministic wording for status. |
| Feasibility vs readiness | Soft checks set `ok: true` (engine line 32); family/paratransit checks use that helper; summary says “can actually attend” (line 114). | Conditional recommendations must not become READY proof. Use independent required dependencies, with explicit confirmation for each. There is no actual READY enum in baseline, so this is an overclaim/readiness risk, not an observed illegal READY transition. |
| Provenance | [`src/domain/activities.ts:22–34`](https://github.com/dude297/c0mpiled-hackathon/blob/26b976233f53d3dede16a92416258e8a3c464cdb/src/domain/activities.ts#L22-L34) is a seeded demo catalog. `dataSource` means explanation source (schema line 60); `verified` means `c.ok` (engine line 108). | AI mode, catalog verification and provider simulation are independent dimensions. Preserve legacy `dataSource`; add separate provenance fields rather than changing its meaning. Do not infer live inventory from a live AI badge. |
| Data quality | Activity fields are TypeScript types, with booleans for accessibility and no unknown/source/freshness state. | B's handoff permits estimated accessibility; a code comment cannot carry uncertainty to the UI or solver. Unknown safety facts should remain unresolved, not become a verified pass. |
| Privacy | AI request includes name, routes, barrier details and workarounds (adapter lines 43–46), which can reveal mobility/hearing. `AI_BASE_URL` may be remote. | “Local-compatible” is supported; “never leaves the laptop” requires runtime proof. A hosted web server's loopback is that server, not the user's laptop. Save/share also changes the privacy boundary. |
| Persistence/authorization | No durable plan store or ownership gate exists. Proposed Supabase handoff uses `select using (true)` ([handoff lines 38–50](https://github.com/dude297/c0mpiled-hackathon/blob/26b976233f53d3dede16a92416258e8a3c464cdb/docs/handoffs/lead-supabase-ai.md#L38-L50)). | Proposal is not a deployed vulnerability. That policy does not restrict reads to possession of an id; do not deploy it with personal profiles. Lead selects restricted share access or omits save/share from MVP. |
| Local inference/fallback | Endpoint selection, timeout and catch-to-mock exist (adapter lines 30–61; route lines 15–18). | Real local runtime/model, latency, cold start and hardware availability remain unverified. AI is awaited before response; configured 20s timeout can delay deterministic results. Offline coordinator/feedback fallback is absent. |
| Scope/complexity | New spec suggests several new directories and `/api/plans` routes; playbook narrows coordinator to its own namespace. | Choose one additive contract and bounded fixture/provider seam. SQLite, Supabase, Google Maps/Calendar and multiple inference runtimes are not prerequisites for an offline P0 loop. |
